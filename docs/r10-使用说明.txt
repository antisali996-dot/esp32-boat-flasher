ESP32 小船 / 遥控器 烧录配对工具（r10：590 转 / 左右各 20°）
================================================================

适用：Windows 10 / 11，经典 ESP32 开发板（ESP32-WROOM / ESP32-D0WD，不是 S3 / C3）。
不需要安装 Python、Arduino IDE 或任何编译工具。全部解压即可用。

本包没有替你烧录任何板子，也没有改动板上现有程序。

本包只包含 r10 这一套固件（版本 20261103-590rpm-r10，590 转、左右 20°）。
旧 580、旧 r7、旧 r9 与更早的固件都不在本包内，也不会被冒充成 r10。


一、先读这四条
--------------------------------
1. 必须把 ZIP 全部解压到硬盘再运行，不要在压缩包里双击。
2. 烧录和配对前，断开动力电池和舵机电源，只保留 USB 给开发板供电。
   小船程序上电会自动把电机驱动到目标转速，不断动力就上电有危险。
3. 本包固件目标 590 转；600 只是“检测到才断电”的软件超速阈值，
   不代表物理转速上限已被证明，也没有经过带载实测。
4. 第一次读串口前会弹一次安全提示（同一次运行只出现一次），确认后再开始。


二、怎么确认板上真的是 r10
--------------------------------
不要看文件名，也不要看 VERSION 文本，只看固件身份串 FWID：

  小船    JAYFWB10-S20-A70-110-U1278-1500-1722-R590-OS600-Cr10-diagshared
  遥控器  JAYFWR10-S20-A70-110-U1278-1500-1722-D1750-2150

前缀里的 B10 / R10 表示 r10 身份（B=小船、R=遥控器），后面依次是
转向 20°、角度 70～110、脉宽 1278/1500/1722；小船另有 590 转与 600 超速阈值，
末尾的 diagshared 表示本版小船已实现现场诊断接口。
与本包不符的一律按“不是 r10”处理：工具会提示升级，不会当作已是最新。


三、界面
--------------------------------
顶部“固件套装”：本包只有一套「590 转 / 20°」（版本 20261103-590rpm-r10）。
选中后右侧显示小船和遥控器的完整固件身份串（FWID）。

串口列表：串口、板子角色、芯片 MAC、固件版本、转向角度、对端地址、说明。
读不到的项写“未知”，不会瞎猜。

主要按钮三个：烧录当前板、配对两块板、备份原固件。
配对行右侧还有一个「只读核验」，用于核验板子当前配置，不写任何东西。

勾选项两个：
- 烧录前先备份原固件（默认关闭，8MB 约 3～5 分钟）
- 即使已匹配也重刷


四、烧录当前板
--------------------------------
1. 选择串口，必要时选择这块板是小船还是遥控器（新板第一次必须选）。
2. 点“烧录当前板”。
3. 确认框会同时列出【板上现在】和【将写入】的角色、目标转速、转向角度、FWID。
4. 写入时强制校验；写完会重启并读回身份，两关都过才显示“烧录完成”。

- 板上固件已经与本包一致时，会提示“无需重复烧录”，不写入；要重刷请勾选“即使已匹配也重刷”。
- 写入失败、校验没报成功、重启读不回来，都算失败，不会显示成功。
- 写入四段：bootloader@0x1000、分区表@0x8000、OTA 选择@0xE000、应用@0x10000。
  不写 0x9000 起的 NVS，所以升级不会顺手抹掉保存的配对地址。
  注意：这只说明本工具的写入范围不覆盖 NVS，不等于“任意旧板的 NVS 升级保留”已经实测过。
- 从 r9 或更早的固件升级到 r10：直接按上面的流程写入即可，固件身份会从旧 FWID 变成 r10 FWID，
  工具据此判断“已是最新”。配对地址属于 NVS，不在四段写入范围内。


五、配对两块板（重要）
--------------------------------
1. 两块板同时插上，分别选择小船串口和遥控器串口。
2. 点“配对两块板”，确认框会列出两块板实际 MAC、当前对端地址和兼容性判断。
3. 只会修改“需要改”的一端；已经指向正确对端的一端会跳过写入与重启。

配对结果按以下状态判定，不会由某个字符串直接判成功：

  未开始 → 已发送绑定 → 收到保存回应，等待身份核验 → 本端配置已核对
  另有：超时／结果未知、已保存但未确认生效、失败／需要人工重新上电核验

关键规则（工具实际执行，r10 不放松）：
- “JAY SAVED REBOOT”只表示保存回应收到，仅作为进展，不单独算成功，也不代表已证明重启。
- 保存后工具会重新发 JAY INFO，要求读到完整的 JAYv4 身份行，并逐项核对：
  角色、本机 MAC 等于写入前核对的芯片、PEER 等于本次目标、FWID 等于本包 r10 FWID。
- 只用 VERSION / STEER 不能替代 FWID；缺字段、半行、无法解析、MAC=READ_FAILED
  全部不放行。
- 只有旧格式兼容行（无 FWID）不会作为核验依据。
- 如果板上是旧固件（FWID 不是 r10），配对前工具会先要求升级，不会拿旧身份凑合通过。

看到以下任一提示时：
- 已保存但未确认生效（SAVED_ACK_NOT_QUEUED / SAVED_ACK_UNCONFIRMED）
- 超时／结果未知
- 失败／需要人工重新上电核验（含 BIND_BLOCKED_PENDING_ERROR）

请这样做：
1. 断开动力，重新上电；
2. 点「只读核验」，选择这块板，确认期望对端；
3. 只有读到完整、匹配的 r10 身份，才会重新判定为已核对。

工具不会自动重复发送绑定，也不会把超时后迟到的成功文字当作本次成功。
本版 r10 固件仍没有工具侧请求流水号，所以工具不声称只靠时间或清空缓冲区就能证明
某条回应一定属于本次请求；这正是要保留“错误锁存 + 人工重新上电核验”的原因。

双端完成条件（全部满足才显示“双端配对配置已核对”）：
- 写入前重新核对两个串口的角色与 MAC；
- 两个串口或两个 MAC 相同 → 禁止写入；
- 已正确的一端跳过绑定与重启；
- 需要改的一端按上面的状态链判定；
- 最后再查询两端：均为 r10 固件、小船 PEER=本次遥控器 MAC、遥控器 PEER=本次小船 MAC，
  且两端都没有未解除的错误/未知状态。

仅一端完成时，会明确写出哪端完成、哪端未完成，以及未完成端处于哪个状态。
重试时先查询，不盲目重发；有待确认错误的一端要先走只读核验。

工具不会显示“无线连接成功”“舵机验证通过”“比赛验收通过”这类结论。


六、备份原固件
--------------------------------
只读整片 Flash，不写不擦。文件保存在 `记录\日期时间-备份-角色\原固件.bin`，
旁边有 SHA256。备份含配对地址，自己留着，别发给别人。


七、分类包（B/C）
--------------------------------
本包如果是分类包，会带 `preset.json`，写明：
- 本组小船的芯片 MAC 与遥控器的芯片 MAC；
- 对应角色在本轮的 r10 FWID；
- 对应镜像哈希见 `构建记录\镜像哈希.txt`。

分类包在写入与绑定前会核对实际芯片地址：地址不符直接拒绝，不会写错板子。
两个分类包（旧小船 / 新小船）用的是同一套运行固件，所以同角色 BIN 相同；
区别只在 preset.json 里记录的小船地址。没有伪造不同 BIN，也没有改动芯片出厂 MAC。

  B 旧小船：小船 24:62:AB:F0:72:94，遥控器 24:62:AB:EF:CF:84
  C 新小船：小船 24:62:AB:F1:36:64，遥控器 24:62:AB:EF:CF:84

通用包（A）没有 preset.json，允许操作任意芯片，但仍按 MAC 核对身份。


八、现场诊断页（r10 新增内容）
--------------------------------
r10 是首次真正实现 COUNT / FAULT 的固件，且只在小船上实现：

- 小船 r10：工具识别到本包 FWID 后，记录期间每 5 秒串行查询一次 COUNT、一次 FAULT。
- 遥控器 r10：遥控器固件不实现这两个命令，工具不向遥控器发送任何自动查询，
  界面显示“遥控器不提供 COUNT/FAULT（只被动记录）”。
- 其它任何固件（r9、旧 580、未知）：不在白名单内，只被动记录，不自动查询。
- 如果板上固件收到不支持的命令并回 `JAY ERROR=UNSUPPORTED_COMMAND`，
  工具会立即停用该条查询并不再重发，不会反复打扰板子。

COUNT 格式：`JAY COUNT boot=<启动标识> ms=<采样毫秒> total=<64位累计计数>`
- boot 按原始文本保存，不假定为整数或终身唯一。
- total 用 64 位无符号整数解析，同时保存原始十进制文本；超出 64 位保留原文并标记解析失败。
- boot 改变 → 新建启动分段；同 boot 下计数倒退只记录异常，不认定重启。

FAULT 证据状态（本轮修复）：界面“故障证据”一行会显示
“完整 / 不完整（缺哪一行）/ 冲突 / 启动分段未确认 / 设备分段未确认 / 待适配（未识别格式）/
  解析失败（数字字段非法）/ 无故障报告”。
只有设备、boot、id 三者都确认且两行配套、无冲突时才会显示“完整”。
“证据完整”只表示两行配套齐全，不代表根因成立或问题已解决。

FAULT 格式（r10 正式格式，已确认）：
  `JAY FAULT CURRENT id=<编号> name=<名字> ms=<毫秒> rpm=<转速> pwm=<值> pulses=<脉冲数> elapsed=<已运行毫秒> integral=<积分>`
  `JAY FAULT PREVIOUS id=<编号> ms=<毫秒> rpm=<转速> pwm=<值> pulses=<脉冲数> elapsed=<已运行毫秒> integral=<积分>`
  `JAY FAULT NONE` 表示当前无故障。
- CURRENT 与 PREVIOUS 只有确认设备、确认启动分段、id 三者都相同才配成一条完整故障。
- boot 为空或占位值时，两行都保留原文并标“启动分段未确认”，之后收到 COUNT 也不会回头补成完整。
- 不同 id、跨启动、跨设备的两行不会被拼成完整故障；配不上的行单独保留原文。
- 同一组同一类型出现内容不同的行 → 锁定“冲突”，保留全部候选原文，不挑一条当完整证据；
  之后再收到旧行、另一类型行或 NONE 都不会解除冲突。
- 完全相同的行重复到达：原文逐次保存，组内去重，不算冲突，也不虚增完整组数。
- 全零的 PREVIOUS 记录照原样保留，不当成“没有故障”。
- 字段数值按 r10 快照的实际类型校验：id/ms/pulses/elapsed 为 uint32，pwm 为 int32（允许负），
  rpm/integral 为 float 且固定两位小数；全部按 InvariantCulture 解析。
  多个小数点、空值、只有负号、NaN、Infinity、非数字字符、越界、小数位不是两位 → 整行判解析失败：
  保留原文与失败原因，不计入有效证据，不补齐/覆盖/解除已有组。
- JAY FAULT NONE 单独记录，不删除历史故障与冲突证据。

导出新增 `FAULT关联.csv`（每组状态、设备/boot 确认标记、id、缺行说明、冲突原因、
两行接收序号与原文）和 `FAULT关联状态变化.csv`（每次状态迁移的时间与原因）；
两者都进文件清单与 SHA256 核验。

本轮另修复了三个已复现的故障关联问题（boot 为空被判完整、同键冲突被判完整、
两行经实际采集仍停在“待适配”），以及一项 P2：FAULT 非法数字（rpm=... / integral=..）
曾被当作有效证据并与 PREVIOUS 组成完整组；现已改为整行判解析失败、不进入关联。
修复后工具测试 612 项通过。

详细说明见同目录 `现场诊断-使用说明.txt`。


九、验证边界（必读）
--------------------------------
已完成：
- 固件由主协调端在其发布环境编译并核对：两端身份文件一致，与备份相比只改了指定的三个宏；
  新 BIN 的大小、SHA256 与内嵌 FWID 都与报告一致；`-DNDEBUG` 复跑 13383 项通过。
- 本包镜像直接从已批准的构建产物复制，未重新编译、未改名、未替换。
- 工具从镜像里反读 FWID 并与清单逐字核对一致（构建时有硬校验，不符即终止打包）。
- 工具模拟测试 612 项通过：原 154+52+61+74+50+33 项、r10 接口 29 项、
  故障关联修复 86 项（覆盖完整/缺行/启动未确认/设备未确认/冲突/重复/跨边界/
  窗口淘汰后导出/导出失败保留数据/ZIP 一致性）、
  FAULT 数值校验 73 项（覆盖非法小数/空值/NaN/越界/非数字字符/InvariantCulture/
  非法行不补齐不覆盖/落盘导出/ZIP 一致性）。
- 分区表解析确认 NVS 0x9000～0xE000 不被四段写入覆盖。

未验证（本机无法证明）：
- 未在真实 ESP32 上烧录、擦除、读取或写入配对；未连接任何设备。
- 未验证真实 USB 串口枚举、CH340 驱动兼容性、DTR/RTS 复位时序。
- 未验证 NVS 在真实升级后保留配对、配对配置真实断电后保持。
- 未验证真实无线链路、摇杆输入、舵机实际角度、电机带载与保护动作。
- 未验证真实两块板同时插入时的完整配对流程与真实重启时序。
- 未验证真实板子上 COUNT/FAULT 的实际输出时序与长时间稳定性。

所以：模拟测试通过 ≠ 设备验证通过。
