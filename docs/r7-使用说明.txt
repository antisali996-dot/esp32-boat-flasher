ESP32 小船 / 遥控器 烧录配对工具（r7：590 转 / 左右各 20°）
================================================================

适用：Windows 10 / 11，经典 ESP32 开发板（ESP32-WROOM / ESP32-D0WD，不是 S3 / C3）。
不需要安装 Python、Arduino IDE 或任何编译工具。全部解压即可用。

本包没有替你烧录任何板子，也没有改动板上现有程序。

本包只包含 r7 这一套固件（590 转、左右 20°）。旧 580 与更早的 590 固件不在本包内，
不会被冒充成更新版本。


一、先读这四条
--------------------------------
1. 必须把 ZIP 全部解压到硬盘再运行，不要在压缩包里双击。
2. 烧录和配对前，断开动力电池和舵机电源，只保留 USB 给开发板供电。
   小船程序上电会自动把电机驱动到目标转速，不断动力就上电有危险。
3. 本包固件目标 590 转；600 只是“检测到才断电”的软件超速阈值，
   不代表物理转速上限已被证明，也没有经过带载实测。
4. 第一次读串口前会弹一次安全提示（同一次运行只出现一次），确认后再开始。


二、界面
--------------------------------
顶部“固件套装”：本包只有一套「590 转 / 20°」（版本 20261103-590rpm-r7）。
选中后右侧显示小船和遥控器的完整固件身份串（FWID）。

串口列表：串口、板子角色、芯片 MAC、固件版本、转向角度、对端地址、说明。
读不到的项写“未知”，不会瞎猜。

主要按钮三个：烧录当前板、配对两块板、备份原固件。
配对行右侧还有一个「只读核验」，用于核验板子当前配置，不写任何东西。

勾选项两个：
- 烧录前先备份原固件（默认关闭，8MB 约 3～5 分钟）
- 即使已匹配也重刷


三、烧录当前板
--------------------------------
1. 选择串口，必要时选择这块板是小船还是遥控器（新板第一次必须选）。
2. 点“烧录当前板”。
3. 确认框会同时列出【板上现在】和【将写入】的角色、目标转速、转向角度、FWID。
4. 写入时强制校验；写完会重启并读回身份，两关都过才显示“烧录完成”。

- 板上固件已经与本包一致时，会提示“无需重复烧录”，不写入；要重刷请勾选“即使已匹配也重刷”。
- 写入失败、校验没报成功、重启读不回来，都算失败，不会显示成功。
- 写入四段：bootloader@0x1000、分区表@0x8000、OTA 选择@0xE000、应用@0x10000。
  不写 0x9000 起的 NVS，所以升级不会顺手抹掉保存的配对地址。
  注意：这只说明本工具的写入范围不覆盖 NVS，不等于“任意旧板的 NVS 升级保留”已经实测过。


四、配对两块板（重要）
--------------------------------
1. 两块板同时插上，分别选择小船串口和遥控器串口。
2. 点“配对两块板”，确认框会列出两块板实际 MAC、当前对端地址和兼容性判断。
3. 只会修改“需要改”的一端；已经指向正确对端的一端会跳过写入与重启。

配对结果按以下状态判定，不会由某个字符串直接判成功：

  未开始 → 已发送绑定 → 收到保存回应，等待身份核验 → 本端配置已核对
  另有：超时／结果未知、已保存但未确认生效、失败／需要人工重新上电核验

关键规则（工具实际执行）：
- “JAY SAVED REBOOT”只表示保存回应收到，仅作为进展，不单独算成功，也不代表已证明重启。
- 保存后工具会重新发 JAY INFO，要求读到完整的 JAYv4 身份行，并逐项核对：
  角色、本机 MAC 等于写入前核对的芯片、PEER 等于本次目标、FWID 符合本轮固件。
- 只用 VERSION / STEER 不能替代 FWID；缺字段、半行、无法解析、MAC=READ_FAILED
  全部不放行。
- 只有旧格式兼容行（无 FWID）不会作为核验依据。

看到以下任一提示时：
- 已保存但未确认生效（SAVED_ACK_NOT_QUEUED / SAVED_ACK_UNCONFIRMED）
- 超时／结果未知
- 失败／需要人工重新上电核验（含 BIND_BLOCKED_PENDING_ERROR）

请这样做：
1. 断开动力，重新上电；
2. 点「只读核验」，选择这块板，确认期望对端；
3. 只有读到完整、匹配的本轮身份，才会重新判定为已核对。

工具不会自动重复发送绑定，也不会把超时后迟到的成功文字当作本次成功。
本版 r7 没有工具侧请求流水号，所以工具不声称只靠时间或清空缓冲区就能证明
某条回应一定属于本次请求；这正是要保留“错误锁存 + 人工重新上电核验”的原因。

双端完成条件（全部满足才显示“双端配对配置已核对”）：
- 写入前重新核对两个串口的角色与 MAC；
- 两个串口或两个 MAC 相同 → 禁止写入；
- 已正确的一端跳过绑定与重启；
- 需要改的一端按上面的状态链判定；
- 最后再查询两端：均为本轮固件、小船 PEER=本次遥控器 MAC、遥控器 PEER=本次小船 MAC，
  且两端都没有未解除的错误/未知状态。

仅一端完成时，会明确写出哪端完成、哪端未完成，以及未完成端处于哪个状态。
重试时先查询，不盲目重发；有待确认错误的一端要先走只读核验。

工具不会显示“无线连接成功”“舵机验证通过”“比赛验收通过”这类结论。


五、备份原固件
--------------------------------
只读整片 Flash，不写不擦。文件保存在 `记录\日期时间-备份-角色\原固件.bin`，
旁边有 SHA256。备份含配对地址，自己留着，别发给别人。


六、分类包（B/C）
--------------------------------
本包如果是分类包，会带 `preset.json`，写明：
- 本组小船的芯片 MAC 与遥控器的芯片 MAC；
- 对应角色在本轮的 FWID；
- 对应镜像哈希见 `构建记录\镜像哈希.txt`。

分类包在写入与绑定前会核对实际芯片地址：地址不符直接拒绝，不会写错板子。
两个分类包（旧小船 / 新小船）用的是同一套运行固件，所以同角色 BIN 相同；
区别只在 preset.json 里记录的小船地址。没有伪造不同 BIN，也没有改动芯片出厂 MAC。

通用包（A）没有 preset.json，允许操作任意芯片，但仍按 MAC 核对身份。


七、验证边界（必读）
--------------------------------
已完成：
- 用 r7 源码快照重新编译两端（Arduino-ESP32 3.0.2），退出码均为 0。
- 固件逻辑回归 13197 项通过（源码端既有记录，不是本工具执行的证据）。
- 工具模拟测试 206 项通过，其中配对状态机 52 项在真实串口回应处理层注入字节流，
  覆盖：正常保存+完整身份、只有保存回应、超时后迟到回应、错误后旧成功文字、
  旧 PEER/错误角色/换 MAC/旧 FWID、READ_FAILED、两种 SAVED_ACK 错误、
  BIND_BLOCKED_PENDING_ERROR 不重绑、部分完成不显示完成、两端已互指零绑定、
  只读核验解除待核验、JAYv4 与旧行并存不降级、半行与分段到达、分类包地址拦截。
- 镜像 FWID 从实际编译产物反读并与清单核对一致。
- 分区表解析确认 NVS 0x9000～0xE000 不被四段写入覆盖。

未验证（本机无法证明）：
- 未在真实 ESP32 上烧录、擦除、读取或写入配对；未连接任何设备。
- 未验证真实 USB 串口枚举、CH340 驱动兼容性、DTR/RTS 复位时序。
- 未验证 NVS 在真实升级后保留配对、配对配置真实断电后保持。
- 未验证真实无线链路、摇杆输入、舵机实际角度、电机带载与保护动作。
- 未验证真实两块板同时插入时的完整配对流程与真实重启时序。

所以：模拟测试通过 ≠ 设备验证通过。

可靠遥控自动恢复仍未完成；600 只是软件阈值；超速、舵机微动和反复停启三个现场问题
都尚无实机验证结论。本轮完成的是工具适配与可信交付，不代表比赛验收通过。
